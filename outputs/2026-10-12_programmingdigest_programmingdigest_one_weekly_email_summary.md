### [如何阅读代码](https://www.seangoedecke.com/how-to-read-code/)

**原文标题**: [How to read code](https://www.seangoedecke.com/how-to-read-code/)

阅读代码不像读普通文本那样从头到尾线性进行；代码为计算机运行而写，常以 diff 形式出现，结构复杂且依赖跨文件。有效方法是先把握整体与调用路径，再多次非顺序扫描，最后才精读 diff。同时，不能完全依赖 AI 代读代码，因为 LLM 生成的代码仍可能存在与人类目标不一致的问题，必须由人审查。

- 📚 英文文本通常按顺序阅读；代码的顺序主要由计算机运行需求决定，不能随意重排。
- ⚙️ 代码经常以 diff 形式被阅读，重点往往是现有代码的细微改动，而非全新程序。
- 🧩 代码结构比文学文本更复杂，依赖可跨整个代码库，大型项目规模也远超普通书籍。
- 🧠 大型程序无法被单人完全理解，阅读代码本质上是分配有限精力的取舍过程。
- ❌ 常见错误是像读书一样顺序硬读、只看 diff、忽略未改动部分，或因复杂而放弃猜测。
- 🔍 推荐“二元扫描/多次扫描”：先看整体结构，再看子结构，最后深入细节。
- 🧭 先选一条重要路径，例如功能 happy path，追踪函数调用关系以理解执行流。
- 🕸️ 多轮按不同线索阅读：沿函数或数据的使用点、调用点扩展，其余部分暂时当黑盒。
- ✂️ 小 diff 可用 Ctrl+F 跳转；大 diff 可在编辑器中 Ctrl+Click 导航，并保持聚焦。
- ✅ 对 diff 有整体把握后，再从头到尾精读，目的是发现之前遗漏的异常代码。
- 🤖 不能完全让 AI 代读代码：LLM 代码可能有对齐问题，技术价值观未必与你或公司一致。
- 👀 可用 LLM 辅助阅读，但必须审查其输出，同时也要亲自仔细阅读代码本身。

### [代码周围的系统——Zarar 的博客](https://zarar.dev/the-system-around-the-code/)

**原文标题**: [The system around the code – Zarar's blog](https://zarar.dev/the-system-around-the-code/)

overview summary
AI 让写代码变得廉价，但真正的交付瓶颈和风险在“代码周围的系统”：流水线、护栏、评审、文档、团队结构、管理方式与学习机制。组织若只买工具、发许可证或强制使用，而不按系统思维重新设计，就会陷入约束转移、局部优化和“试点炼狱”。成功路径是把一组可适配的组件嵌入组织，并用系统指标而非使用量指标衡量。

- 🧠 核心转变：AI 主要解决了“写代码/打字”，价值转向决定、指定、验证和把系统生产化。
- 🏗️ 结构产生行为：反复出现的问题通常源于结构、反馈回路、延迟和积累，而非离事件最近的人或代理。
- 🔍 三个解释层级：事件最浅，行为模式较好，结构才是能改变结果的地方；AI 评论多停留在事件层。
- 🚦 吞吐由最慢环节决定：AI 让 PR 增多，但评审、平台、安全等瓶颈会吞掉收益。
- 📊 Faros AI 数据：高 AI 团队合并 PR 增 98%，评审时间增 91%；约束只是从写代码转移到评审。
- ⚖️ 限制增长：增长回路被评审容量等刹车限制；加许可证、代理或强制令无效，杠杆在刹车。
- 🕳️ 转移负担：买 token、强制使用、排行榜、试点炼狱、英雄团队、频繁换工具、先裁员，都是症状性修复。
- 🧾 数据警示：MIT NANDA 称 95% 组织对 GenAI 投资零回报；Gartner 预计 2027 年底超 40% agentic AI 项目被取消。
- 🧩 未变之事：结构决定行为；现在是最佳构建软件时期，试错成本暴跌；设计、纪律、分解仍是前提。
- 🪓 小批量是前提：代理在清晰、有界、可验证的小变更上成功；DORA 指出 AI 收益依赖小批量工作。
- 🧱 设计原则更重要：深模块、小接口、单一职责、DRY、MECE、清晰接缝，因为代理上下文小且照字面执行。
- 🧭 不存在可购买的“AI SDLC”：没有银弹流程；真正要做的是一组组件与组织情境的适配。
- 🧮 一致性模型：工作、人员、正式组织、非正式组织必须与战略匹配；只改一个盒子，其他会抵消收益。
- 🚰 流水线就是 AI 战略：写代码是最小部分；可观测性、CI、测试、部署、反馈回路决定 AI 能否放大价值。
- 🛤️ 按变更类型分车道：机械变更、明确功能、模糊/跨切面、探索性工作，需要不同工作流和人工角色。
- 🔁 循环而非聊天：可重复、脚本化、状态存盘、每轮小任务和全新上下文；长聊天会耗尽上下文并累积错误。
- 📚 代码即规范：代码和测试记录“系统做什么”，文档只保留“为什么”；过期文档会生成自信但错误的代码。
- 🛡️ 标准要可执行：指南是建议，护栏是强制；用技能、钩子、棘轮、CI 检查把判断变成可执行约束。
- 🔍 评审从读代码变为验证证明：作者必须证明可用；AI 初审、人类按风险审查，把精力放在资金、认证、数据迁移等高风险处。
- 📋 流而非 Scrum：代理像可拉取工作池；看板、WIP 限制、审查队列管理和端到端流动比故事点更合适。
- 🤝 角色模糊：设计师、PM、分析师也能构建，工程师更产品化；PR 成为通用交接，代码所有者、保护分支、预览部署是护栏。
- 🧑🏫 经理变赋能者：少派单追进度，多塑造流程、补能力、教学、清除阻塞；仍要做 1:1、成长、心理安全和身份转变支持。
- 🌱 个人系统与学习：个人工作流也应技能化、循环化；警惕把思考外包，尤其别让初级工程师失去理解力。
- 🩺 Day 1 是诊断：识别所处循环，只做该循环响应的杠杆动作，并用交付系统指标衡量一个月。
- 📌 结论：工具会变，系统会留下；不要 AI-first，而要 System-first。

### [](https://godobject.dev/blog/packing-binary-is-fun-actually/)

**原文标题**: [Packing Binary Is Fun, Actually](https://godobject.dev/blog/packing-binary-is-fun-actually/)

overview summary
文章讲述作者因不满 JSON 而动手设计二进制序列化格式 jBin：从简单的 `fwrite` 出发，逐步实现 varint/tag、schema 语言、词法/语法/语义分析、动态 JSON→二进制打包，以及基于 Visitor 的多语言代码生成与 CLI。最终把示例 JSON 体积压缩约 80%，并感叹“二进制打包其实很有趣”。

- 🧨 起因：作者看到推文说“真正开发者不用 JSON”，出于逆反心理决定自建二进制格式，本以为只是 `fwrite`，结果造出完整 schema 语言。
- 🧮 二进制打包基础：ASCII 字符串按字节写入；数字若按 ASCII 存会浪费空间，因此需要类型、长度等元数据。
- 🏷️ 标签设计：从 `[类型][长度][数据]` 起步，再用 continuation bit / MSB 支持变长，解决长度超过 127 的问题。
- 🔢 varint：采用 LEB128 风格，每字节 7 位数据 + 1 位延续位，小数字占更少字节。
- 🧩 schema 思想：像 C struct 一样，类型由 schema 声明，不必在每个值旁边重复存储类型。
- 📝 语法设计：使用 `编号. 名称: 类型`，message/enum/end，支持 list、map、union、默认值、package/import，尽量比 protobuf 简洁。
- 🏗️ 实现流程：用 C++ 实现 Lexer → Parser → AST → Semantic Analyzer → 动态 Packer → Codegen → CLI。
- 🔍 编译器组件：Lexer 把源码切成 token；Parser 构建 AST；语义分析两遍建立符号表并校验类型、重复字段号、循环依赖等。
- ⚡ 动态打包：读取 JSON + schema，按 AST 查字段号与类型，直接编码二进制，无需生成或编译 C++ 包装代码。
- 🧳 代码生成：用 Visitor Pattern 支持不同目标语言生成器，例如 C 生成零依赖结构体、pack/unpack、setter/getter 等。
- 💻 CLI：使用 cxxopts 实现 `build` 和 `pack` 命令，分别从 schema 生成代码或把 JSON 打成二进制。
- 📉 效果：示例 `{"name":"Pranav","health":100}` 从约 35 字节降到 9 字节；复杂 Character JSON 从 401 字节降到 80 字节，减少约 80%。
- 🎉 结论：作者原本只想省 JSON 空间，意外完成了 lexer、parser、AST、语义分析、二进制打包器和多语言代码生成器；二进制打包其实很好玩。

### [](https://compiler.club/aho-corasick/)

**原文标题**: [Colin James - Aho-Corasick](https://compiler.club/aho-corasick/)

Aho-Corasick 自动机用于在序列中同时匹配多个子串。它从字典树出发，通过 BFS 构建后缀链接与输出链接，再将 trie 确定化为 DFA，使扫描文本时每步转移可常数时间完成。文章依次讲解 trie、后缀链接、输出链接、伪代码、自动机构建与演示。

- 🌳 字典树（trie/前缀树）用带字符标签的 n 叉树存储字符串，公共前缀被共享，完整模式所在节点会被显式标记。
- 🔗 后缀链接用于转移失败时恢复匹配，指向当前节点字符串的最长后缀，且该后缀是 trie 中某模式的前缀。
- ⚙️ 后缀链接通过 BFS 构建：根及其子节点指向根；其他节点从父节点的后缀链接出发，若存在对应字符边则指向该边目标，否则沿后缀链接继续上溯，直到根。
- 💡 示例中扫描 `suitems` 到表示 `suit` 的节点后没有 `e` 边，可沿后缀链接继续，从而匹配 `su[item]s`。
- 📌 输出链接用于处理一个匹配同时包含其他模式作为后缀的情况；节点若对应输出模式，还需沿输出链接继续输出。
- 🔵 输出链接计算依赖后缀链接：若节点的后缀节点是输出节点，则输出链接指向它，否则指向前缀节点的输出链接；如 `{spin, pin, in}` 中到达 `spin` 对应节点后还需输出 `pin` 和 `in`。
- 🧾 伪代码使用队列进行 BFS：先初始化根及子节点的后缀链接，再逐节点寻找可用字符边，设置 `node.suffix` 与 `node.output`。
- 🤖 后缀链接和输出链接只是中间步骤；之后再做一次 BFS，把所有转移静态解析为 DFA：根缺失边自循环，其他节点缺失边转到其后缀节点的转移目标。
- 🗂️ 最终自动机会将输出合并为集合；由于许多转移指向根，离线实现常适合使用稀疏矩阵存储。
- 🧪 文章提供构建 Aho-Corasick trie 的演示，并推荐原论文《Efficient String Matching: An Aid to Bibliographic Search》作为进一步阅读。
