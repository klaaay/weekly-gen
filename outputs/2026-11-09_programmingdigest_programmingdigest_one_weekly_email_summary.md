- 💳 订阅：使用 Claude Pro 与 GitHub Copilot Pro，取消 OpenAI；Copilot 仅用于自动补全。
- ⚖️ 总体判断：AI 是“勇敢新世界”，既能帮助人学习、做工具、联系朋友，也会制造企业垃圾与冲击数学界；关键在于用工具帮助人，而不是替代人的声音与创造性。

### [更新向量数据库绝非易事](https://softwaredoug.com/blog/2026/08/18/update-graph-vector-db.html)

**原文标题**: [Updating a vector database is no simple thing](https://softwaredoug.com/blog/2026/08/18/update-graph-vector-db.html)

概述总结：文章聚焦向量搜索在生产环境中的“软肋”——数据更新与写入。以 HNSW 和 Lucene 为例，说明向量更新通常变成“删除 + 插入”、墓碑删除、多 segment 图并行搜索、写前日志与合并重建等机制，以及查询性能与写入可见性之间的权衡；并建议用真实生产流量做影子测试，主动了解数据库实现与厂商社区，而不是只依赖静态基准。

- 🧭 公共向量搜索基准常假设“一次性建索引再搜索”，但真实系统索引持续变化，如职位过期、社交媒体不断新增内容。
- 🕸️ HNSW 通过连接相似项的图来导航搜索，是 Elasticsearch、Weaviate、Milvus、QDrant、Vespa 等系统的核心结构。
- 🔁 向量更新通常不是原地修改，而是 upsert：先删除旧位置，再插入新位置；多数系统用墓碑标记删除，保持图可导航但不返回已删除结果。
- 🧱 Lucene 维护多个 segment/图：新插入先进入新图，并通过写前日志和定期提交变得可搜索；查询会并行搜索多个图，之后合并/重建为更大的图。
- ⚖️ 提交频率会显著影响查询延迟与数据可搜索速度；文章举例：每 1000 个向量提交时延迟约 0.063665s，每 50000 个向量提交时约 0.001764s。
- 🧩 不同系统有不同取舍：Vespa 维护单图并处理并发更新查询；Weaviate 用墓碑但保持单图；QDrant、Milvus 等常用可变非图结构承接新插入，长期数据进入只读优化图。
- 🧪 HNSW 更像为“冻结数据 + 召回/延迟”基准优化，写入更新像后补问题；聚类类算法可能写入更快但牺牲查询精度。
- 🛡️ 选型时应做影子测试：用候选数据库搭建集群，复制真实索引与查询流量，持续监控和调优；同时主动接触厂商与社区，成为知情、积极的购买者。

### [消息队列 - Alex Ewerlöf 笔记](https://blog.alexewerlof.com/p/message-queues)

**原文标题**: [Message Queues - Alex Ewerlöf Notes](https://blog.alexewerlof.com/p/message-queues)

文章从系统设计角度解释消息队列为何存在、如何工作、何时适用及其局限，并以照片分享应用为例说明队列在异步处理、解耦、缓冲流量和隔离故障方面的价值，同时涵盖确认机制、投递语义、分区、背压、死信队列、持久化及 Kafka、SQS、RabbitMQ 的对比。

- 🖼️ 照片上传示例：同步串行处理会带来高延迟、资源低效、失败脆弱和流量峰值问题；拆分为独立服务并用队列可快速响应用户、隔离失败并缓冲峰值。
- 🔌 队列是生产者与消费者之间的缓冲区，消息暂存到消费者处理，双方解耦并可独立扩展、替换。
- ✅ ACK 确认机制：消费者处理完显式确认后才删除消息；若崩溃未确认，消息会重投给其他消费者，避免丢失。
- 🚫 防重复处理：SQS 用可见性超时，RabbitMQ 用 unack 与超时重入，Kafka 用分区与消费者组 1:1 分配避免竞争。
- 📨 投递保证：至少一次可能重复但默认常用；至多一次不重复但可能丢失；恰好一次很难，通常用至少一次加幂等消费者、去重键或事务实现。
- 🎯 适用场景：异步工作、突发流量、生产消费双方扩缩容或硬件需求不同、不能丢失工作；强低延迟同步场景慎用，队列会延迟错误反馈。
- 🧩 分区与顺序：分区提升吞吐，消费者组并行消费，但消费者数不能超过分区数；分区键要权衡顺序性与均匀分布，避免热分区。
- 🌊 背压与 DLQ：生产快于消费时需自动扩缩容、拒绝新消息或让客户端重试，并监控队列；毒消息设置最大重试后进入死信队列并告警。
- 💾 持久化与容错：Kafka 等将消息落盘、跨 broker 复制并保留窗口，可防队列故障丢消息，也支持重放历史消息。
- ⚖️ 产品对比：Kafka 适合高吞吐、持久化、事件流和重放；SQS 托管简单，标准队列高吞吐但尽力排序/至少一次，FIFO 保序/恰好一次但吞吐较低；RabbitMQ 适合复杂路由的传统消息代理。
- ⏳ 更新观点：队列不消除失败，而是延迟并隐藏失败；应监控最旧消息年龄而非仅队列深度，并预先定义持续失败消息的处理策略。

### [程序员的悖论：小事](https://theprogrammersparadox.blogspot.com/2026/10/little-things.html)

**原文标题**: [The Programmer's Paradox: Little Things](https://theprogrammersparadox.blogspot.com/2026/10/little-things.html)

文章总结了作者多年编程中形成的若干“小习惯”，核心是提前准备、消除未知、用函数表达意图、保持命名与代码清晰，并通过抽象、重构和对细节的重视来提高开发效率与代码可靠性。

- 🛠️ 编码前尽量做好准备工作：环境、磁盘、外设、家具，以及日志、错误处理、配置、密钥和安全基础都应先就绪，减少后续干扰。
- ❓ 不要留下疑问：如果不知道“做什么”或“为什么做”，现在就查清楚，不假设、不忽略、不拖延。
- 🧩 多用函数给代码块命名：函数名应简洁明确，通常是一个动词作用于输入名词，避免晦涩命名；函数也可替代注释，便于审查、分解和重构。
- 🧱 拆分前置条件与核心逻辑：把断言、错误处理、小计算等放在函数开头，让核心逻辑不被干扰；每个后续要用的数据都放进独立变量，相关逻辑聚在一起。
- 🔁 不要害怕大幅重构：发现方向错误或逻辑颠倒时立即修正，不要因为已投入时间而继续硬撑，否则会变成时间黑洞。
- 👀 重视可读性细节：代码要便于几个月后自己回看，也能让隐藏问题更容易暴露。
- 🏷️ 对命名保持敬畏：认真找到技术层面和业务领域中真正准确的名称；错误命名会吸引 bug，甚至长期传播造成困扰。
- ➰ 谨慎对待循环：能不用就不用，循环要拆出来并能证明其必要性；循环往往是性能问题的源头。
- 📈 不要硬磨大量样板代码：如果感觉要用 50 小时重复劳动，就退一步寻找更好的抽象或泛化方式。
- 🧠 不要耍小聪明，要聪明而清晰：显式写清楚通常更安全，语法糖可能变成以后会踩到的地雷。
- 🎯 代码不是系统本身，但它是控制系统行为的关键：代码规模越大，风格、格式、组织、一致性和细节越重要；要追求精确，以便在关键时刻可靠地完善代码。

### [我们用 MySQL 取代 Redis 处理库存预留——而且它成功扩展了（2026）- Shopify](https://shopify.engineering/scaling-inventory-reservations)

**原文标题**: [We replaced Redis with MySQL for inventory reservations—and it scaled (2026) - Shopify](https://shopify.engineering/scaling-inventory-reservations)

Shopify 将结账库存预留系统从 Redis 迁移到 MySQL，借助 `SKIP LOCKED`、单库存单位一行、有界资源池、复合主键与连接可观测性，在高并发峰值流量下实现扩展目标；最关键的发现是瓶颈并非查询或 CPU，而是结账链路中长期占用数据库连接的问题。

- 🛒 超卖保护包含 Reserve 与 Claim：支付开始时短时预留库存，支付成功后永久扣减库存账本，必须同时避免超卖和少卖。
- 📈 规模要求极高：Shopify 占美国电商 14% 以上，2025 黑五峰值每分钟销售额达 510 万美元，库存预留需承受突发流量并保持 ACID。
- ⚠️ Redis 旧架构的局限：预留与库存账本分属两个系统，Claim 无法与 MySQL 扣减组成单一原子事务，可能导致超卖或少卖，且不支持多地点库存感知。
- 🧱 新方案核心：用“一件可售库存一行”替代“一个商品一行加数量列”，并用 MySQL 8 的 `SKIP LOCKED` 跳过已锁行，降低行竞争。
- 📦 有界资源池：每个商品/地点最多维护 1000 行可预留池，由库存账本补充；极端秒杀时池耗尽会触发内联补充并用锁避免惊群，保证有货买家不被拒绝。
- 🔑 复合主键减少锁：原型使用自增 ID 时每次预留产生两个行锁；改为包含过滤列的复合主键后降为一个行锁，提升高并发吞吐。
- 🧩 隔离级别与锁顺序：使用 `READ COMMITTED` 避免 gap/supremum 锁阻碍补充；统一 reserve/claim 的加锁顺序，避免循环等待死锁。
- 🚀 批量查询：对多商品购物车用 `UNION ALL` 合并预留查询，减少数据库往返并改善高负载延迟。
- 🔍 真正瓶颈是连接：延迟和 CPU 看似正常但吞吐受限；通过 SQL 注释标签加 ProxySQL 解析，统计各业务流程的连接持有时间，发现结账链路其他代码长期占用连接。
- 🧹 优化结果：清理结账链路减少主库 50% 读取和 33% 事务，并重新评估 InnoDB 线程并发配置；峰值时写 CPU 低于 50%、读 CPU 低于 16%。
- 🔄 灰度切换：Redis 与 MySQL 以“影子模式”双写并行验证，Redis 仍为真源；确认正确性与性能后按 Pod 逐步切换，并保留 kill switch 可回退。
- 💡 经验教训：旧决策需随新特性重审；从小型原型和可观测性开始；若指标不匹配（低 CPU 高排队），应检查完整链路而非只优化数据库引擎。

### [精通 AI 需要时间和练习](https://www.seangoedecke.com/getting-good-at-ai-takes-time-and-practice/)

**原文标题**: [Getting good at AI takes time and practice](https://www.seangoedecke.com/getting-good-at-ai-takes-time-and-practice/)

文章主张“用好 AI”并非记住几个提示词技巧，而是需要长期练习的实践能力；这些能力包括提供上下文、理解模型边界、审查 AI 输出、快速筛选冗余信息等。作者认为，刻意回避 AI 可能让人落后，但完全依赖 AI 也不可取，因为 LLM 会放大专业能力的价值，而专业能力仍需靠手动实践积累。

- 🧠 反驳“AI 无需学习、技巧终会过时”的观点：真正用好 AI 需要长期技能与持续练习。
- 🧩 提供正确上下文：不要指望 AI 读心，要说明问题、连接必要工具，并解释“为什么”要做这件事。
- 🔍 了解模型能力边界：AI 在某些任务上很强、某些很弱且难以预测；新模型主要提升旧强项，能力感相对持久。
- ⚠️ 识别 AI 常见错误：审查 AI 代码不同于审查人类代码，要警惕表面流畅、过度工程、为虚构边缘情况引入复杂方案等“错位”错误。
- 👀 快速略读 AI 冗余输出：学会在大量啰嗦表述中抓取具体主张和证据，避免浪费时间和精力。
- 🕰️ 这些技能未必很快过时：即使工具进步，人机协作的“半人马时代”可能持续数十年。
- 🛠️ 其他重要技能：判断何时放弃或引导 AI 会话、拆分任务、决定何时信任或验证、用较小模型控制成本、跟进当前技巧。
- ⚖️ 不应完全回避 AI，也不应全盘依赖：LLM 会奖励专业能力，而专业能力最好靠手工积累；但不实践就永远用不好 AI。
- 🤝 把 AI 当作能力极不均衡的“奇怪同事”：像管理者一样花时间摸索如何发挥其价值；刻意回避者可能被善用者甩下。
