### [](https://addyosmani.com/blog/brownfield-agentic-engineering/)

**原文标题**: [Brownfield Agentic Engineering | AddyOsmani.com](https://addyosmani.com/blog/brownfield-agentic-engineering/)

在老旧代码库中引入代理式工程，核心是让隐藏约束可见、让低成本变更可信；代码仍是事实来源，额外知识只补代码无法推断的部分。要按风险分区，先锁定行为、留下研究产物、把重复错误变成脚手架，最后才并行化。

- 🧱 棕地系统：仓库不是系统实际行为的完整描述，机构知识、遗留服务和其他团队依赖在代码之外；写新代码前必须学会并验证这些约束。
- 🤖 无监督代理易产出“能跑”但设计错误、测试脆弱的代码；目标应是安全地降低变更成本，而非放任自动改。
- 🚦 风险分区：绿区=安全、测试好、隔离强，可让代理紧循环；黄区=质量混杂，先写表征测试；红区=认证、计费、权限、工资等敏感区，需人类结对或暂不做。
- 🧭 分区是操作流程：人画地图，不是代理；代理会先挑最吓人的文件。分区只有挣得才能移动，区域决定动作强度。
- 📝 写下代码说不出的内容：业务/团队细节、为何这样设计的权衡、未强制执行的规范、领域规则、外部约束与反直觉实现的历史背景，别写其他。
- 🗂️ 研究要留下持久产物：黄/红区先做只读理解备忘录，含入口、负责人、调用方、既有抽象、测试、生产信号、历史与开放问题，并引用来源。
- 🧠 计划用干净上下文，人类选路径；实现发现地图有误就停止；评审从验收标准反向开始，避免测试只证明实现却漏掉需求。
- 🧰 把重复纠正变成脚手架：指令记录特殊事实，技能封装可复用流程，插件提供受治理权限；重复评审意见应转成 lint、hook、类型、测试或技能。
- 🔒 代理出错时不要静默修 diff；拒绝规则、限权凭证、CI 检查不靠记忆，脚手架成为团队不愿重复付费的失败记录。
- 🧪 从零风险工作开始：先用表征测试锁定当前行为，包括丑陋部分；不要让同一代理会话成为测试唯一作者，然后做机械转换、死代码/未用导出清理。
- 🎛️ Netflix GraphQL 式切换：新旧路径并行、重放/影子流量、对比载荷，匹配后才推广；只被生产流量理解的界面天然是红区。
- 🧩 迁移以完整单元完成：一条路线端到端做完并移除旧依赖，别留半迁移，否则代理看到矛盾先例。SWE Refactor Bench 称“Blindness”，520 次代理运行仅 28 次通过迁移审计等。
- ⚙️ 大迁移经验：Bun Zig→Rust 用 11 天约 50 工作流处理 53.5 万行，每单元两个对抗评审，旧测试套件作合并门，且先写移植指南；Anthropic 先用一次性小迁移试规则。
- 📏 迁移单元大小是关键：VB6→C# 简单功能 92% 行为等价，复杂功能 47%。Stripe 370 万行 TypeScript 单 PR 靠数月 codemod、无代理；Google 说明原子变更随代码库增长而变小；Spotify 每月 650+ 代理 PR；Asana 两周清 Enzyme 积压，约 1.2 万美元生成成本，但仍人工评审。
- 💡 代理改变的是“尝试多个实现方案的价格”，不是选择方案所需证据。Shopify 用代理门控、按屏检查点在 12 周内重写 Shop 应用，但商家应用仍是棕地问题。
- 🧑⚖️ 最后才并行化：更多生成代码应带来更有选择性的人类评审，而非更少所有权。先让一个单元有可靠裁判、恢复路径和可吸收的评审格式；并行会放大瓶颈。
- 🔍 自动评审先看意图、不变式、测试结果、parity 不匹配、回滚路径；人类优先看最大爆炸半径与最弱 oracle。worktree 只隔离变更，不隔离行为，可能共享 Git 元数据、凭证、本地服务和网络。
- 📊 代理让模糊性有了价格：跟踪前置时间、评审分钟、人工干预、逃逸缺陷、回滚、oracle 不匹配、遗留抑制；迁移看旧导入、新路径流量、parity 不匹配、移除的旧依赖。全流量仍走旧路径的绿测是白忙。
- 🧾 下次代理修首页级问题时，应留下比修复更多的东西：合成用户旅程、所有权记录、回归测试；下一位工程师和代理继承什么很重要。

### [用数学（和 Rust）再节省 100TB 内存 | Cloudflare 博客](https://blog.cloudflare.com/saving-100-tb-of-ram-with-math/)

**原文标题**: [Saving another 100TB of RAM with math (and Rust) | Cloudflare Blog](https://blog.cloudflare.com/saving-100-tb-of-ram-with-math/)

Cloudflare 的 Pingora Backend Router 因一致性哈希库 pingora-ketama 占用过多内存，团队通过数学分析、Rust 数据结构优化、将每服务器哈希数减少 90%，并以新旧哈希环并存和分层迁移控制风险，最终全球节省超过 100TB RAM；相关改进已进入开源 pingora-ketama crate。

- 🏗️ Cloudflare 规模达数千服务器、PB 级内存与数百万 CPU 核，资源吃紧，微小优化会被巨大规模放大。
- 🚨 性能团队发现 PBR 中 pingora-ketama 的一致性哈希结构内存异常，部分场景达 6GB。
- 🔁 一致性哈希把可缓存请求按 URL 稳定路由到后端，使每个数据中心只需保存一份缓存内容。
- ⚖️ Ketama 允许按服务器权重（如磁盘空间）分配哈希数量，但为满足合规和缓存特性组合，需要多个独立哈希环，数量呈指数增长。
- 📈 数学推导显示：增加每服务器哈希数可降低负载不均衡，但收益递减；32 位哈希还会因碰撞引入误差。
- 🧱 存储优化：将 Point 中服务器索引从 u32 改为 u16，并用字节数组和 getter 绕过 Rust 对齐限制，节省 25% 内存。
- ✂️ 根据误差公式，团队将每服务器哈希数减少 90%，而未造成明显误差。
- 🔀 迁移时新旧哈希环并存，按请求哈希稳定选择环，并保留快速回滚路径。
- 🌐 分层上线：从小型验证位置到更大数据中心群，再推广至全球，控制缓存抖动和影响范围。
- 👀 监控后端选择、环版本、连接错误、进程内存、启动时间、缓存行为和回源流量，达到 100% 后移除旧环。
- 💾 最终 PBR 内存使用减少 100TB，叠加 DNS 团队上月节省的 100TB。
- 🦀 改进已进入开源 pingora-ketama crate：v2 环支持紧凑存储、更快排序、可扩展基础哈希数；v1 保持原样，二者可同时运行。
- 💡 启示：简单或“显而易见”的设计可能隐藏优化空间，深入数学与数据能带来跨系统收益。

### [](https://hawksley.dev/blog/i-dont-like-passkeys)

**原文标题**: [I don't like passkeys | Ethan Hawksley](https://hawksley.dev/blog/i-dont-like-passkeys)

文章认为 passkeys 虽是防钓鱼的优秀技术，但当前生态对个人用户尚不成熟：恢复与锁定风险、硬件密钥限制、同步生态碎片化，使作者更推荐“随机密码 + 第三方密码管理器 + 独立 TOTP”。

- 📢 科技巨头持续强推 passkeys，Google、Microsoft 等不断提示用户启用，甚至称可“尽可能跳过密码”或“让账户无密码”。
- 🛡️ passkeys 本身很安全：绑定站点，能防假登录页钓鱼；采用非对称加密，服务器泄露后无法还原。
- 🏢 它更适合企业环境，不适合个人安全；个人更常面临永久锁号、自动封禁和设备丢失风险。
- ⚠️ 标准登录钓鱼被消除，但可能带来虚假安全感；账户安全仍由最弱恢复方式决定，如短信、邮件链接、安全问题。
- 🔑 硬件密钥不能备份或迁移 passkeys，只能添加或删除；需买 2–3 个并逐站注册，成本高且难扩展。
- 🔢 硬件密钥的 discoverable credentials 有账户上限，通常 25–100 个，高端最多约 300 个；超出需删号或再买密钥。
- 🍎 Apple/Google 推动同步 passkeys 绑定其账户；一旦账户被自动封禁，会不可逆失去第三方账户的所有 passkeys。
- 🔄 FIDO 正改善互操作与导出，但目前碎片化、不一致，尚不够成熟；密码反而能手动导出。
- 🧩 用 Bitwarden、KeePassXC 等存 passkeys 仍像与平台对抗，自动填充体验不如密码，原生应用外尤其不一致。
- 💻 在他人电脑上使用不便：硬件密钥可能无端口，同步 passkey 需信任电脑，Hybrid Transport 的二维码+蓝牙也有兼容与失败问题。
- 🚫 作者结论：passkeys 对企业有理由，但对个人生态未成熟；独立 TOTP 虽有钓鱼风险，但锁号风险更日常。推荐随机密码 + 第三方密码管理器 + 独立 TOTP；对曾复用密码者是进步，对其他人目前是退步。
- ✍️ 作者 Ethan Hawksley，华威大学计算机科学学生，也是《The Second Maintainer》作者。

### [](https://bastrich.tech/coupling-and-cohesion/)

**原文标题**: [Back to Coupling and Cohesion - Daniil Bastrich](https://bastrich.tech/coupling-and-cohesion/)

本文指出，SOLID、GRASP、KISS 等设计原则在实践中大多可归结为对耦合与内聚的管理；耦合衡量组件间关联强度，内聚衡量组件内部目标一致性。作者主张用实际任务数据量化两者，追求低耦合、高内聚，但不要为原则而原则。

- 🧩 耦合：一个组件变化导致其他组件也要变化的强度；内聚：组件各部分是否围绕单一目的。
- 📐 可通过实际任务统计测量：耦合看单个任务触碰的组件数及投入分布；内聚看单个组件涉及的关注点及投入分布。
- 🧮 耦合公式为 1 - Σx_i²/(Σx_i)²；内聚公式为 Σx_i²/(Σx_i)²，与多样性/集中度指标相关。
- 🔑 耦合按“变更/任务”跨组件测量，内聚按“被变更组件”跨关注点测量，二者不是互补值，也不一定相加为 1。
- 🧾 示例：密码长度校验分别存在于注册和改密表单；修改规则时耦合约 0.48，两个表单内聚均为 1。
- 🎯 低耦合、高内聚能让开发者更专注当前任务，减少后续修改、bug 和维护成本，提升软件质量。
- 🏛️ SOLID 等原则可还原为耦合/内聚：SRP 对应高内聚；OCP、LSP、ISP、DIP、DRY、LoD 主要降低耦合；KISS 则通过减少需同时掌握的信息降低复杂度。
- ⚠️ 局限：抽象可能带来 CPU/内存开销，嵌入式或低延迟场景需权衡；一次性脚本、PoC 也不必过度设计。
- ✅ 核心建议：依据未来变更可能性和实际约束做设计，不要为了遵循原则而引入不必要的抽象和复杂性。

- 🎯 目标用一句话说明项目目的;背景解释动机与上下文,且文档应无需外部解释即可理解
- 🔗 链接相关文档(测试计划、功能规格、相关系统及前代设计文档)
- ✅ 目标应表达对用户/团队/公司的价值,而非实现细节;非目标明确划定范围外事项
- 🎬 场景用真实案例描绘系统如何运作;图表能极大帮助评审者理解架构
- 📖 术语表定义读者可能不熟悉的内部术语,优先使用可识别术语或内联定义
- 📊 SLO 用可衡量指标(可用性、延迟、规模)消除模糊,监控/告警说明如何检测故障
- ⏱️ 时间线将项目拆分为里程碑,应产出对干系人有用的人工制品,便于早期纠错
- 🔌 接口描述用户界面、API/CLI 语义或文件格式,无需过度纠结 UI 细节
- 🏗️ 依赖/基础设施说明编程语言、运行硬件、持久化数据位置,重点关注难以更换的依赖
- 🔒 安全部分考虑威胁、攻击面、信任边界;隐私部分说明敏感数据处理、保留期限、访问权限与保护措施
- ⚖️ 法律部分针对受监管领域或开源许可说明合规与选择理由;日志部分设计关键事件、级别、存储、保留与访问
- ❓ 开放问题记录设计缺陷、信息缺口、方案纠结,并给出选项与下一步;解决后移入已解决问题并保留完整讨论
- 🔄 考虑的替代方案简要说明强力备选及为何放弃,无需事无巨细
- 🗣️ 完成后应与团队分享并收集反馈,推动项目前进而非陷入争论与混乱
