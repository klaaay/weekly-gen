### [如何制作误差扩散二维码](https://www.andrewt.net/dithered-qr-codes/wtf/)

**原文标题**: [How to make error-diffused QR codes](https://www.andrewt.net/dithered-qr-codes/wtf/)

本文介绍如何制作带抖动效果的个性化二维码：二维码由功能图案和数据模块组成，数据模块可被改造以嵌入低分辨率图片；通过误差扩散抖动与专门针对数据模块的两遍误差扩散，可减少噪点、提升观感，但必须在美观与可扫描性之间权衡。

- 🔳 二维码本质：把少量字节编码成可从照片读取的方格阵列，设计上能抵抗模糊、角度和部分缺失。
- 🧩 结构分为功能图案和数据模块：功能图案用于定位，必须清晰；数据模块存数据，可在定位后适度修改。
- 🖼️ 嵌图思路：缩小或改造数据模块，用像素中心存数据，其余空间放图片，得到低分辨率单比特图。
- ⚪⚫ 抖动基础：低色深时通常不直接阈值化，而用棋盘格或拜耳滤镜制造中间色调。
- 🌊 误差扩散：Floyd-Steinberg 从左上开始阈值化，并把亮度误差扩散到未处理邻域，使平均亮度更准、图案更自然。
- 📉 二维码加误差扩散：不规则抖动可掩盖数据模块造成的椒盐噪声，但 147×147 单比特图仍会显得很噪。
- 🧮 两遍误差扩散：第一遍专门按数据模块颜色处理并扩散误差，第二遍常规扩散，能显著让图像更干净。
- 🛠️ 生成器进阶：可旋转二维码、调整编码设置，寻找更美观的替代编码。
- ⚠️ 修改数据模块：可借纠错能力改动少数像素，类似中间放 logo，但会明显影响扫描可靠性。
- 📱 实际使用：适合大屏幕或海报；纸质传单、褶皱、光线差等场景需要更多冗余和纠错。
- 🖨️ 边距与背景：生成器常无白边，需留边距才可靠；边距颜色要与定位图案中心相反，反色二维码需黑底。
- 🧾 浏览器缩放：未用 CSS 禁用插值时会模糊放大图像，影响扫码；你的手机能扫不代表别人低端机或打印件能扫。

### [](https://kciter.so/posts/railway-oriented-programming/en/)

**原文标题**: [Railway-Oriented Programming | kciter.so](https://kciter.so/posts/railway-oriented-programming/en/)

本文系统介绍 Railway-Oriented Programming：从副作用与错误处理出发，比较 LBYL、EAFP、纯函数、Guard Clause 与 try-catch，再借 Functor、Monad、Result 将成功与失败抽象为轨道，并讨论恢复、错误类型约束、Monad Comprehension 与嵌套容器问题。
- 🚧 副作用是函数内部影响外部世界的行为，常见于 I/O 和函数内错误，会让程序流程难以预测。
- 🔍 错误处理主要分为 LBYL 和 EAFP：前者先检查条件再行动，后者先执行并捕获异常。
- 🧮 纯函数对相同输入总返回相同结果，可提高可预测性，但无法解决 I/O 与未预见错误。
- 🛡️ Guard Clause Pattern 把防御条件放在逻辑开头，减少嵌套并提升可读性。
- 🧯 try-catch 适合高层调用和必须保持不崩溃的服务端，但可读性较差，且需预知可能异常。
- 📦 Functor 像盒子：解包值、应用函数、再重新包装，通常通过 map 转换内部值。
- 🚫 Option 与 Result 可分别处理空值和异常，map 会在容器上下文中安全变换值。
- 🔗 Monad 解决 Functor 嵌套问题，通过 flatMap 避免出现 Result<Result<...>>。
- 🛤️ ROP 由 Scott Wlaschin 提出，把逻辑抽象为成功轨道与失败轨道，函数顺序执行，程序不应 panic。
- ♻️ Result 可实现成功、失败与恢复轨道，recover 或 rescue 能让失败重新回到成功轨道。
- 🧷 用 sealed class 约束错误类型后，可通过模式匹配让编译器检查所有情况，更安全地处理异常。
- 🧵 Monad Comprehension 如 Scala 的 for/yield 或 Kotlin 的 binding，可减少多步依赖造成的嵌套。
- 🧳 嵌套容器问题如 Result<Option<T>> 需要 HKT 与 Monad Transformer 解决，但语言支持有限，选型需考虑环境。
- ⚖️ 不建议每个函数都使用 Result，否则会损害可读性，应只在真正需要的函数中使用。
- 🦀 Rust 没有 try-catch，但借鉴了 ROP 思想，用 Result 与模式匹配处理错误。

### [单体优先](https://martinfowler.com/bliki/MonolithFirst.html)

**原文标题**: [Monolith First](https://martinfowler.com/bliki/MonolithFirst.html)

Martin Fowler 认为，新项目应优先采用“单体优先”策略：即使未来可能受益于微服务，也先从单体开始。因为成功微服务案例大多来自过大的单体拆分，而从零构建微服务常陷入严重麻烦；微服务适合复杂系统，但存在显著“微服务溢价”，早期应优先速度与反馈，待边界稳定后再逐步演进。

- 🏗️ 几乎所有成功的微服务故事，都始于一个变得过大、随后被拆分的单体。
- ⚠️ 几乎所有从零构建微服务系统的案例，最终都遇到了严重麻烦。
- 💸 微服务是有效架构，但有“微服务溢价”，即管理一组服务的成本会拖慢团队，简单应用更适合单体。
- 🚀 新应用初期应验证想法是否有用，优先快速迭代和反馈，避免承担微服务开销。
- 🧭 微服务只有在边界良好且稳定时才有效，但即使经验丰富的架构师在初期也很难划对边界。
- 🧩 单体优先可先探索正确边界，并逐步发展微服务所需的前提条件。
- 🛠️ 执行方式包括：精心设计模块化单体；从边缘逐步剥离微服务；整体替换并用“可牺牲架构”快速上市；先做粗粒度服务再细化。
- 🔁 不能假设任意单体都能拆成微服务；多数系统模块依赖过多，强行拆分容易混乱。
- 🤔 反方观点认为，从微服务开始可适应开发节奏、按服务划分团队、便于扩展，尤其适合系统替换；但团队最好已有微服务经验。
- 📊 目前证据仍少，关于单体优先的建议应视为暂定，远未达成一致。

### [尽力而为的排他锁究竟有什么用？](https://gaultier.github.io/blog/what_good_is_a_best_effort_exclusive_lock_anyway.html)

**原文标题**: [What good is a best-effort exclusive lock, anyway?](https://gaultier.github.io/blog/what_good_is_a_best_effort_exclusive_lock_anyway.html)

本文解释 CockroachDB 在 SERIALIZABLE 隔离级别下，`SELECT ... FOR UPDATE` 只提供“尽力而为”的排他锁：它适合缓解高并发竞争，但不能作为正确性保证；正确性应依赖 SERIALIZABLE 的冲突检测与重试。

- 🧩 背景：同事在 Kratos 中用数据库行锁防止一次性代码被两个请求同时使用，正确性至关重要。
- 🐘 在 Postgres/MySQL 中，`SELECT ... FOR UPDATE` 提供真正的排他锁：其他加锁读/写会阻塞到事务提交或回滚。
- 🪳 CockroachDB 虽支持该语法，但在 SERIALIZABLE 下文档称其为 best-effort，不应依赖它保证正确性，等待顺序也可能不被保留。
- ⚠️ 直接改用 READ COMMITTED 可让 `FOR UPDATE` 变成完整排他锁，但会失去 SERIALIZABLE 保证，引入并发异常，且混用隔离级别更难维护。
- 🧠 SERIALIZABLE 的意义：并发事务产生与某个串行顺序相同的效果；检测到读写/写写冲突时，最多一个事务提交，其余重启或重试。
- ✅ 因此，只要事务一开始触碰正确的行，即使没有锁，应用重试失败事务后也能保证正确。
- 🎟️ `FOR UPDATE` 存在的原因：高竞争场景（如 1 万请求抢同一张票）下，所有事务都重试代价高昂；让部分事务等待可显著降低竞争。
- ⏳ 优化写法：先 `SELECT ... FOR UPDATE` 对目标行取得 best-effort 锁，让并发事务在此等待，再执行昂贵的更新逻辑，减少后续争用。
- 💡 best-effort 的原因：这些锁是快速、内存中、未复制的锁；若发生 lease transfer 或 range split/merge，锁会被直接丢弃，甚至不需要节点崩溃。
- 🧭 结论：SERIALIZABLE 很好但有时昂贵；可考虑条件写入、写入不同 range，或在合适场景利用 best-effort 等待来优化性能。

### [](https://addyosmani.com/blog/brownfield-agentic-engineering/)

**原文标题**: [Brownfield Agentic Engineering | AddyOsmani.com](https://addyosmani.com/blog/brownfield-agentic-engineering/)

在棕地代码库中引入智能体工程，核心不是让智能体无监督重写，而是让隐藏约束显性化，并让便宜变更可信：用分区、持久研究、harness、特征测试、完整迁移单元和结果指标，把自主性绑定到爆炸半径、可观测性与可恢复性上。

- 🧱 棕地系统不是仓库能完整描述的：机构知识、胶带式修补、遗留服务和其他团队的依赖都在代码之外。
- ⚠️ 智能体无监督改旧代码风险高：可能“能工作”但系统设计错误、测试脆弱，甚至把业务依赖的丑陋行为“修掉”。
- 🚦 用绿/黄/红分区管理：绿区测试好且隔离，可紧密循环；黄区需先写特征测试；红区涉及认证、计费、权限、薪酬等，必须人类配对或不做。
- 🧭 分区规则要成为操作程序：由人画地图；黄转绿需特征测试和模块负责人审查；区域决定允许的动作。
- 📝 写下代码说不出的东西：业务/团队特定细节、历史权衡、未强制执行的约定、领域规则、外部约束和反直觉实现的原因。
- 🔍 让研究跨会话留存：对黄红区做只读理解备忘录，记录入口、负责人、调用者、抽象、测试、生产信号、历史与开放问题，并引用文件、issue 或仪表盘。
- 🧪 研究后干净上下文规划：列出方案触及文件、保持的不变量、如何回滚；人类选路径；实现发现地图错误就停止；审查从验收标准反向开始。
- 🛠️ 把重复纠正变成 harness：指令记录异常事实，技能封装流程，插件提供受控访问；同一审查意见重复出现就转为 lint、hook、类型、测试或技能。
- 🧷 从零风险工作开始：先解释系统，生成特征测试锁定当前行为，包括丑陋部分；不要让写测试和让测试通过的智能体是同一会话或唯一作者。
- 🔒 特征测试锁定现状：旧系统丑陋行为可能是业务所依赖，智能体可能会“修复”它却让测试仍绿；生产级表面可用影子流量和回放对比。
- 🧩 迁移以完整单元完成：新路径可用且旧依赖可证明移除；半成品迁移会让智能体看到矛盾先例，能删除旧路径才算完成。
- 🏭 大迁移案例的启示：Bun 的 Zig→Rust 有移植指南、对抗审查和全套测试作为合并门；Stripe 用 codemod；VB6→C# 显示单元越小效果越好；Asana 清 Enzyme 积压但成本是生成成本，不是节省研究。
- 💸 智能体改变的是尝试多种实现的成本，不改变选择所需证据：可并行实现多个方案并对测试、性能评估，但决策仍需证据。
- 🧵 最后才并行：并行会放大既有瓶颈；先让一个单元有可靠裁判、恢复路径和可吸收的审查格式；自动审查先看意图、不变量、测试、差异和回滚；人类关注最大爆炸半径和最弱 oracle。
- 📊 用结果而非生成行数衡量：跟踪前置时间、审查分钟、人工干预、逃逸缺陷、回滚、oracle 不匹配、遗留抑制；迁移看旧导入、新路径流量、一致性差异和移除的遗留依赖。
- 🧭 智能体给模糊性标价：部落约定变成反复审查评论；这使维护工作的价值更容易被量化。
- 🎁 下次智能体修 homepage 类表面时，应留下合成用户旅程、归属记录和回归测试，而不只是修复。
