### [](https://calibreapp.com/blog/native-lazy-loading)

**原文标题**: [Lazy Loading Images and Media: How Far Ahead Browsers Fetch | Calibre](https://calibreapp.com/blog/native-lazy-loading)

懒加载只需一个 HTML 属性（loading="lazy"），无需 JavaScript，能跳过用户不会滚动到的图片、嵌入内容和视频，加快首屏加载并节省数据流量。但实际使用率很低，且常见误用会拖慢性能，尤其是错误地懒加载 LCP 图片。文章系统讲解了 lazy、eager、fetchpriority 的正确用法，各浏览器的预取距离差异，以及三种常见错误和排查方法。

- 📉 **使用现状**：Chrome 数据显示仅 26% 的页面加载对图片用了 lazy，iframe 只有 1.5%，音视频几乎为零；而 17% 的页面错误地懒加载了 LCP 图片，反而变慢。
- 🏷️ **属性本质**：`loading` 只有 `lazy` 和 `eager` 两个值，不设置时默认为 `eager`；预加载扫描器会立即抓取 eager 图片，而 lazy 会等到布局完成且元素接近视口才加载。
- 🧩 **适用范围**：可用于 `<img>`、`<iframe>`、`<video>`、`<audio>`；图片和 iframe 支持广泛，音视频支持尚有限（仅 Chrome/Edge 150+）。
- ✅ **该懒加载什么**：几乎所有首屏以下的媒体都应收懒加载，iframe 收益最大，音视频会推迟文件、海报和自动播放。
- 📏 **浏览器预取距离**：Chrome 随网速动态调整（慢速 2G 最多提前 8000px），Firefox 固定四边 600px，Safari 提前一整个视口；Safari 的 lazy iframe 需进入屏幕才加载。
- ⚠️ **错误一：懒加载 LCP 图片**：延迟图片请求至布局后（约晚 262ms），直接拖慢最大内容绘制，首屏主图应保持 eager。
- ⚠️ **错误二：遗漏宽高**：lazy 媒体在布局后才到达，需为图片、视频、iframe 指定 `width`/`height` 或 CSS `aspect-ratio`，避免布局偏移。
- ⚠️ **错误三：全部懒加载**：模板中无差别加 `loading="lazy"` 会损害性能，首屏内容应保持 eager。
- 🎯 **推荐策略**：LCP 图片用 `fetchpriority="high"`，首屏其他图片保持默认 eager，首屏以下用 `loading="lazy"`；`<picture>` 中属性应加在 `<img>` 上。
- 🖼️ **懒渲染：CSS content-visibility**：`content-visibility: auto` 可跳过屏外内容的布局与绘制，渲染时间从 232ms 降至 30ms，配合 `contain-intrinsic-size` 防止滚动条跳动。
- 🔍 **懒加载任意内容**：用 `IntersectionObserver` 可延后地图、聊天组件、CSS 背景图、Firefox/Safari 音视频及按需 JS 模块，`rootMargin` 可自定义触发距离。
- 🛠️ **排查方法**：在 DevTools 的 Network 面板筛选 Img/Media，禁用缓存后重载不滚动，观察首屏请求，再滚动查看被延迟的请求，并检查 Elements 面板中实际渲染的 HTML。
- 🏁 **总结**：合理运用 `preload`、`loading="lazy"` 和 `fetchpriority` 几乎是无成本的性能收益，但用错地方反而会拖慢页面。

**原文标题**: [Declarative partial updates  |  Web Platform  |  Chrome for Developers](https://developer.chrome.com/docs/web-platform/declarative-partial-updates)

- 🧩 背景：HTML 仍按顺序自上而下交付，常迫使等待整页或依赖重型框架；Chrome 提出 Declarative Partial Updates 来解决这一问题。
- 📡 乱序流式：使用处理指令 `<?marker name="...">` 作为占位符，配合 `<template for="...">` 在后续流中替换内容，实现 HTML 乱序到达和按就绪更新。
- ⏳ 临时内容：`<?start>` 和 `<?end>` 可包住“Loading…”等占位内容，模板到达后替换；模板内可再放 `<?marker>` 以支持多次追加更新。

- 🏝️ 用例：支持岛架构、内容就绪即流式发送、按性能优化 HTML 顺序（如延后 mega menu），不再受顺序阻碍。
- ⚠️ 限制：`<template for>` 只能更新同一父元素内处理指令；放在 `<body>` 可访问整个文档；`<?end>` 可选；移动处理指令或流式目标可能产生意外/错误。
- 🧪 兼容与 polyfill：`<template for>` 已进入 HTML 标准但未全浏览器支持；template-for-polyfill 可在其他浏览器提前使用；未来考虑客户端 include、版本化防覆盖、打补丁时清洗。
- 🛠️ 新插入 API：新增 `setHTML`、`replaceWithHTML`、`beforeHTML`、`prependHTML`、`appendHTML`、`afterHTML` 等静态方法，命名一致，替代旧 API 的差异和歧义。
- 🌊 流式 API：每个操作都有 `streamHTML`、`streamReplaceWithHTML`、`streamBeforeHTML`、`streamPrependHTML`、`streamAppendHTML`、`streamAfterHTML` 等流式版本，可用 Streams API 写入或从 fetch 管道传输。
- ⚙️ 选项与安全：静态/流式方法可通过 `options.sanitizer` 使用 Sanitizer；Unsafe 版本默认关闭清洗并可 `runScripts: true`，需信任输入；`textStream()` 简化 fetch 到流式 HTML。
- 📦 用例：SPA 可流式更新大块内容，插入 footer/partial 等通用内容；但依赖 JS 的内容不宜用于首屏。
- 🔒 限制：与 Trusted Types 需 `createParserOptions`；流式移动元素会出问题；`streamHTMLUnsafe` 类似主解析器，会处理 `<template for>` 并延迟 `defer` 脚本。
- ✅ 标准化与 polyfill：新插入/流式 API 正在纳入 HTML 标准，Chrome 148 实验、计划 Chrome 155；html-setters-polyfill 只缓冲不流式，Safari 不支持 `setHTML`/Sanitizer。
- 🔗 组合威力：把流式 `<template for>` 与新插入 API 结合，可加载带处理指令的页面轮廓，再流式套用模板完成 SPA 式局部更新；Chrome 还在开发更多相关 API。

- 📏 常见场景是 iframe 组件测量自身高度，并通过 `parent.postMessage({ type: 'resize', height }, '*')` 请求父页面调整尺寸。
- ⚠️ 父页面若直接使用 `event.data.height` 设置高度，就没有验证发送者、窗口身份或数据格式，等于公开 API。
- 🕵️ 攻击一：任意来源窗口可伪造 resize 消息，把高度设为 1 或 999999，操纵宿主页面布局。
- 🔒 修复一：使用严格相等检查 `event.origin !== WIDGET_ORIGIN`；不要用 `includes` 或宽松正则，因为 `widget.example.com.evil.net` 会通过。
- 🚫 不要允许 `"null"` origin；无 `allow-same-origin` 的沙盒 iframe 会得到不透明 origin，且所有此类 origin 都序列化为 `"null"`。
- 🪟 攻击二：同源但错误的 iframe 也能通过 origin 检查，例如两个同源组件互相冒充发送 resize 消息。
- ✅ 修复二：检查 `event.source !== iframe.contentWindow`，把消息绑定到你实际嵌入的那个窗口。
- 📦 攻击三：合法 `postMessage` 数据仍可能是负数、`1e9`、字符串、`null`、`NaN`、`Infinity`、缺少 `type` 或形状错误的对象。
- 🧪 修复三：先验证载荷是非 null、非数组对象且 `type === 'resize'`，再要求 `height` 是有限数字，并按布局策略钳制到如 100–1200px。
- 🛡️ 完整处理器顺序：校验 origin → 校验 source → 校验 payload → 钳制数值 → 应用尺寸，并为每次接受、拒绝或钳制记录原因。
- ⚙️ 生产环境应把日志替换为空操作或指标，同时必须考虑速率限制，合并 resize 消息并限制拒绝日志频率。
- ✉️ 发送方不要把 `targetOrigin` 写成 `'*'`；应指定唯一允许接收的精确 origin，避免消息泄漏到意外父页面。
- 🔁 回复消息时可使用已验证值：在处理器内执行 `event.source.postMessage(..., event.origin)`。
- 🧰 多宿主嵌入时，让宿主在嵌入时声明自身，但声明只是配置，不是授权；敏感消息前仍要对照已登记的受信嵌入 origin。
- 🧩 若页面不需要接收消息，最稳妥的加固是完全不注册 `message` 监听器。
- 🌐 相关主题还包括 `sandbox` 属性、CSP `frame-ancestors` 和用于私有双向管道的 `MessageChannel`。
- 💻 演示使用两个真实 origin（CodePen 与 GitHub Pages），本地可运行 `python3 serve.py`，通过 4173/4174 两个端口复现跨源场景。

### [简介 | Lift HTML 文档](https://lift-html.js.org/)

**原文标题**: [Introduction | Lift HTML Documentation](https://lift-html.js.org/)

Lift HTML 是一个轻量级库，用于构建 HTML Web Components，通过增强页面已有 HTML 来添加交互，而不是在客户端渲染或水合。它试图填补大型 JavaScript 框架与零散脚本之间的空白，同时保留服务端渲染、类型安全、HMR 和渐进增强等开发体验。

- 🧩 遵循 HTML Web Components 模式：HTML 在服务器渲染，组件只增强已有 HTML。
- ⚡ 解决现代 Web 开发的两难：不是大型 JS 中心框架，也不是随意散落的 script 标签。
- 🖥️ 服务器端可继续照常生成 HTML；组件类型用 TypeScript 声明，支持“转到定义”和属性类型检查。
- 🔌 客户端可继续使用现有 JS 工具链，已集成 SolidJS Signals 和 Alien Signals，也可用喜欢的库渲染标记。
- 🛠️ 已有构建流程可用 HMR 和 dead-code elimination；没有则可使用 CDN 导入进行无构建开发。
- 📏 极低开销：最小约 150 字节 gzip；核心包约 600 字节 gzip；Solid 包约 3.4KB gzip。
- 📚 可用包：@lift-html/core、@lift-html/solid、@lift-html/tiny，分别面向基础、响应式和极简场景。
- ✅ 关键特性：极小体积、框架无关、完整 TypeScript、原生 Web 标准、可选反应式状态、开箱即用 HMR。
- 🌐 选择 HTML Web Components 的原因：服务端渲染利于 SEO 和首屏性能，渐进增强，可访问性更好，心智模型更简单。
- 🧪 示例展示 copy-button 与 SolidJS 的 my-button 组件，使用 CDN 时总代码约 3.41KB gzip。
- 📦 下一步包括安装指南、快速开始、基础用法、组件、示例和互操作性。
- 👥 社区资源包括 GitHub 仓库、在线演示和代码示例。
