- 🚀 产品领导者和 PM 把未验证想法、日期或时间框架推上路标，会加剧问题。
- 🧭 用“可预测性 vs 结果”框定取舍，才能触及公司文化、激励、项目模式与产品模式差异，也决定 AI 是带来更好结果还是让人更快跑错方向。

### [Lock your GitHub Actions · Hugo van Kemenade](https://hugovk.dev/blog/2026/lock-github-actions/)

**原文标题**: [Lock your GitHub Actions · Hugo van Kemenade](https://hugovk.dev/blog/2026/lock-github-actions/)

本文介绍 GitHub Actions 新增的工作流锁文件功能：通过 `gh-actions-lock` 扩展，将原先固定到完整 SHA 的做法改为使用版本标签并生成锁文件，同时支持依赖更新工具与 CI 验证，从而在安全性和可维护性之间取得平衡。

- 🔐 过去建议把 Actions 固定到完整 SHA，因为标签可变，可能被用于供应链攻击。
- 🧩 先安装 `gh` CLI 扩展：`gh extension install github/gh-actions-lock`。
- 🔒 在仓库运行 `gh actions-lock`，会把 workflow 中的 SHA 固定改为 `vX.Y.Z` 标签，并生成 `.github/workflows/actions.lock`。
- 📄 锁文件记录每个 Action 的 `ref`、`commit` SHA、`owner_id`、`repo_id`，由工具自动生成，不应手动编辑。
- 🤖 Renovate 和 Dependabot 已支持锁文件，定期更新时会同步更新锁文件；建议使用 cooldowns。
- ✅ GitHub 建议在 CI 中验证锁文件，可添加独立 job 运行 `gh actions-lock --verify`，确保锁文件同步且未损坏。
- 🧰 验证示例使用轻量的 `ubuntu-slim` runner，并将 `gh-actions-lock` 固定到 `v0.4.1`。
- 🛡️ `zizmor` 是 GitHub Actions 安全 linter，`v1.32.0` 起支持锁文件，建议在 pre-commit 中配置使用。
- 📌 修改 workflow 后需重新运行 `gh actions-lock` 重新锁定；新增 workflow 文件时尤其需要。
- 🚀 提交修改后的 workflow 和锁文件即可完成；文中还给出了 Pillow、CPython 等示例。

**原文标题**: [Horrible public key tricks:](https://maurycyz.com/projects/badcert/)

文章介绍了作者用“虚荣 RSA 公钥”在受信任 TLS 证书中隐藏可读消息的做法，以此讽刺传统证书体系复杂、证书频繁过期以及 CA 安全实践问题；作者认为该证书仍可用于正常 HTTPS 加密。

- 🔐 作者不满 SSL/TLS 的 ACME 流程、证书短期过期和 CA 曾使用极弱密钥（如“4”）等现状，但并非反对加密流量本身。
- 🧮 RSA 公钥由模数 n 和公开指数 e 组成；标准 e 为 65537，CA 通常拒绝非标准 e，因此可操作空间在 n 的 2048/4096 位“用户可控”部分。
- 🪄 生成虚荣密钥的方法：先随机选 p、q 得到 n，再把消息写入 n 的字节以影响 Base64 显示；随后令 q≈n/p 并取附近素数，使消息通常保留在 n 的上半部分。
- 📜 用该私钥生成 CSR，通过 certbot 手动 ACME 流程让 CA 签名；支持单域名或通配符证书，续期可重复提交 CSR 并自动化。
- 🧩 Base64 按 3 字节分组，消息可能错位不可读；由于证书布局固定，调整消息位置通常少于 4 次尝试即可成功。
- 🛡️ 该技巧会降低私钥熵，但作者认为仍足够安全，类似“固定部分 n”的压缩思路；不过脚本不检查 q 过近或 d 过小等潜在风险。
- ⚠️ 对公开网站而言，即使私钥未来泄露，现代 TLS 的前向保密仍可防止被动窃听，攻击者需实施中间人攻击。
