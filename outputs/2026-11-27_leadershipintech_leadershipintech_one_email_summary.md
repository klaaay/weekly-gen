# [Reorganized](https://leadershipintech.com/newsletters/2417-reorganized)

### [重组 - 作者：Mike Fisher - Fish Food for Thought](https://mikefisher.substack.com/p/reorganized)

文章从一句常被误归为古罗马人的重组抱怨谈起：它实际出自二战美军通信官 Charlton Ogburn Jr. 对 Merrill’s Marauders 的回忆，后来又被误传给 Petronius 等人。作者借此讨论员工感受到的“变化加速”：技术采用确实更快，但论文与专利的颠覆性未必同步上升；真正压在员工身上的，往往是企业主动规划的变革和重组。重组会打断团队熟悉度，带来可测量的恢复成本，因此领导者应先把这笔成本算清楚，再用可被听见的解释和事后校验来减少“变化是你做的、感受却由员工承担”的落差。

- 📈 **企业变革密度上升**：Gartner 研究人员在 2023 年 HBR 文章中报告，2022 年员工平均经历 10 次有计划的企业变革，2016 年为 2 次；同期愿意支持企业变革的员工比例从 74% 降到 43%。
- 🧪 **机组熟悉度实验**：NTSB 1994 年对重大航空事故的研究中，有数据可查的事故里 73% 发生在机组首次一起飞行当天，44% 发生在首次共同航班；NASA 模拟实验显示，疲惫但彼此熟悉的机组错误约为休息充分但从未合作机组的一半，新组合机组错误超过两倍。作者总结：熟悉度胜过休息。
- ⚙️ **重组恢复成本**：作者曾在一家公司用实验速度衡量改组成本：把完整团队整体转向新项目，平均约 6 周恢复到此前速度；增删成员则约 12 周。也就是说，改变团队方向约损失一个半月，改变成员构成约损失一个季度。
- 🧠 **团队经验比司龄更关键**：Wipro 超过 1000 个软件项目的研究显示，成员此前合作过的团队表现更好；在公司年限这类多数领导者常用的用人依据并不能稳定预测表现，特定岗位经验则有预测力。Tuckman 的 forming、storming、norming、performing 四阶段在真实工作团队中较难确认，但新团队确实需要数周磨合，每次成员变化都会重启部分磨合时钟。
- 💡 **主动改变与被动改变**：Steven Levitt 的抛硬币实验让参与者对换工作、结束关系等重大决定随机选择改变或维持现状；被提示改变的人更可能行动，并在六个月后报告更幸福，但参与者自愿加入且幸福为自报，需谨慎解读。作者指出，自己选择的变化带有自己写的故事，被强加的变化则附带别人的幻灯片和重新学习新同事工作方式的成本。
- 🛠️ **下次重组前先算账**：作者建议在批准下一次重组前统计员工今年吸收了多少有计划变革、这次会让多少人跟从未合作过的同事共事，并把相关人数乘以 12 周；若重组仍值得，就从中留出部分时间做解释，用几句话写清受影响者会觉得公平的“为什么”，能说的说、不能说的承认。
- 💬 **检查沟通是否真的到达**：William H. Whyte 1950 年在 Fortune 写道，沟通最大的敌人是沟通的幻觉；这句话常被误归给 George Bernard Shaw。作者建议重组一个月后问三位受影响员工“为什么发生”，如果答案与领导者版本不像，就说明还需要继续解释。

### [Tiden · 面向编程智能体的意图验证](https://tiden.ai/?utm_source=leadershipintech&utm_medium=newsletter&utm_campaign=tiden_launch)

Qase 团队推出 Tiden，一款面向编码 agent 的意图验证工具，用来应对编码速度变快、交付质量却跟不上的问题：agent 写测试的依据是它自己刚写的代码，而不是你最初的请求。Tiden 会在会话开始前记录意图，把它整理成可验证的承诺（promises），并读取代码仓库自动起草产品规格，标出没有测试证明的部分；只要还有承诺没有被测试证明，它就不允许结束会话、允许合并或发布。它和 Claude Code、Cursor、Copilot、Codex、Gemini CLI 一起使用，已接入 GitHub、GitLab、Jira、Linear、Notion 和 Azure DevOps，目前提供免费试用。

- 🧩 **意图捕获与关闭闸门**：`tiden intent start "Add rate limiting to the public API"` 在会话开始时记录意图，示例中捕获 3 条承诺；写完代码后执行 `tiden intent close` 被拒绝，会话保持打开，并显示 delta `TIDEN-377 (no_test)`，指出「Pro 超过 600 返回 429」没有任何测试覆盖。
- ⚙️ **补齐测试后才放行**：agent 根据缺口补写测试，再执行 `tiden run exec -- go test ./...`，run #11 通过 4 项测试后，`tiden intent close` 才返回 ready for review，合并决定仍交给用户。
- 📊 **承诺与测试逐条对应**：分支页面逐条列出承诺及其测试证据：Free 每分钟超过 60 次请求返回 429（2 个测试通过）、每个 429 都带以秒为单位的 Retry-After（1 个通过）、Pro 超过 600 返回 429（1 个通过），3/3 全部通过才进入可合并状态。
- 🔍 **规格自动生成与保持同步**：连接 GitHub 或 GitLab 后，Tiden 读取代码和 Jira、Linear、Notion 中的工单，自动起草规格供人工审阅，并标出无测试证明的规格；每次合并都会起草规格更新，包括未经过 Tiden 的合并，使规格随代码变化。
- 🛡️ **发布质量门**：发布视图按组件给出结论，例如 2.6.0：205/205 条规格由实际运行过的测试证明、13/13 个组件在发布时健康、该版本范围内 0 个未解决生产问题，并冻结发布时刻的快照；生产错误可回溯到对应发布版本，再由 agent 修复并补上缺失测试。
- 💡 **人工决策入口**：对没有测试证明的规格，团队可以选择 Ask for a test 或 Accept the risk；代码审查仍属于原有评审人，Tiden 只回答「这是不是你要求的」以及「哪部分有测试证明」。
- 🌐 **现有工具集成**：可连接 GitHub、GitLab、Jira、Linear、Notion、Azure DevOps；已有规格或测试套件可以直接导入，不要求从零开始。
- 🧭 **与代码审查和规格驱动工具的区别**：CodeRabbit、Greptile 等读 diff 判断代码写得好不好，Tiden 核对是否符合原始请求；GitHub Spec Kit、OpenSpec、Kiro 侧重让 agent 编码前先写规格，Tiden 则对每次变更对照规格校验，并让规格随代码保持最新，且不限定 agent。
- ✅ **可渐进采用**：开始前不需要已有规格或测试：接入 GitHub 或 GitLab 后由 Tiden 读取代码和工单起草规格，标记未覆盖项，再由 agent 补测试；官方表示自建类似流程的难点不在一次性脚本，而在长期维护意图、规格与测试之间的映射关系。

### [AI 正在改变代码审查，工程负责人需要跟上。—— Ido Green](https://greenido.dev/2026/10/26/ai-is-changing-code-review-engineering-leaders-need-to-catch-up/)

AI 让写代码成本降低，但多数工程组织仍在用把写代码视为瓶颈的流程；Will Larson 在 Imprint 的实验显示，PR 合并量达到两年前的 4 倍，审查时间中位数从 33 分钟升至 77 分钟，同时事故下降，表明瓶颈已转向审查与验证。文章主张为低风险变更建立机器验证的快速通道，把投资从更多 AI 审查转向自动化验证，并围绕快速、可验证的变更重设计软件交付系统。

- 📊 **瓶颈迁移**：Will Larson 在 Imprint 的实验显示，工程师合并的 PR 数量达到两年前的 4 倍，PR 审查时间中位数从 33 分钟升至 77 分钟，同时报告事故下降；更多代码、更长审查、更少事故说明瓶颈已从编码转向审查与验证。
- 🧩 **低风险快车道**：对满足严格机器验证标准的小型、隔离变更提供自动批准，敏感或复杂变更仍要求人工审查；早期实验中仅约 10% 变更符合条件，重点不是取消审查，而是停止把昂贵的人工注意力花在低价值处。
- 💡 **重设计流程**：AI 采用不应只自动化既有工作流，而要围绕新的经济性重设计；增加会评论代码的 AI 审查者、再让其他代理回应评论，可能只是模拟人工审查，未必提升软件质量。
- 🛠️ **验证优先**：更值得投资自动验证：强测试、静态分析、安全检查、可复现构建和明确风险边界。AI 能生成代码，工程系统必须提供该代码可安全发布的证据；人类判断应更多用于制定策略、处理模糊决策，并在失败暴露缺口时改进系统。
- 🎯 **度量瓶颈**：跟踪审查延迟、PR 吞吐、逃逸缺陷、事故以及审查 AI 生成代码所耗工程时间，用这些指标识别真正的瓶颈。
- ✅ **实施路径**：为小型、隔离变更定义明确资格规则，仅在必需检查通过时自动批准；安全敏感代码、共享基础设施、关键业务逻辑和广泛影响变更保留人工深入审查；先在一个团队或仓库做受控实验，度量周期时间和质量后再扩展。
- 🔄 **失败学习**：自动化变更引发事故时，应改进检查和资格规则，而不是只依赖更多人工警惕；优化目标应是安全发布软件、更短交付周期和更少缺陷，而非 AI 生成代码行数或合并 PR 数。
- 🧭 **结论**：若工程组织保留相同瓶颈，AI 无法兑现完整生产力收益；竞争优势属于围绕快速、可验证变更重设计整个软件交付系统的团队。

### [隐形工程团队 - Manager.dev](https://www.manager.dev/newsletter/invisible-engineering-teams)

文章讨论工程团队在组织中的可见度差异，指出低可见度团队常被忽视、背锅、难获晋升和编制，甚至更易受裁员影响；作者基于管理 DevOps、产品、内部工具和 CEO 重点项目等不同可见度团队的经验，提出连接信息管道、追问“如果停做会怎样”、把业务干系人带入团队三项做法，以系统性提升团队及工程师的可见度。

- 🧭 **可见度光谱**：团队默认可见度取决于工作性质：CEO 重点项目约 10/10，DevOps、安全或平台团队约 2/10，经典产品团队 6/10，内部运营工具团队 4/10；做基础性项目也会临时降低可见度。
- ⚠️ **低可见度症状**：常见表现包括：支持所有大项目却难获功劳、故障时先被指责；持续接收运维杂活；晋升校准会上其他管理者不认识团队成员；工程师与业务结果脱节。
- 🏢 **管理风险**：管理不可见团队会面临业务决策和重点变化带来的突袭、成员被重组、增编困难，裁员时也往往受冲击最大。
- 🔗 **连接信息管道**：不要只在 Slack 或邮件泛泛发布，要明确目标受众和其偏好的渠道；对不同层级定制信息：直属上级需要上下文，C-suite 只要影响；例如先询问高管偏好，再连续数月发送每周简短影响邮件。
- 🎯 **反向验证价值**：用“如果我们不做会怎样”检验工作重要性：停止维护后业务会否受损、哪些用户会抱怨、公司内谁会最受影响；若没人介意，就应调整方向。
- 🔄 **引入干系人**：把业务方请进团队会议，层级越高越好，并收集成功故事回传团队；让干系人认识成员后，更可能阅读更新，从而扩大信息管道。
- ✅ **系统性提升**：作者强调这些工作值得做，系统性执行能同时提升团队和工程师的可见度，并要确保自己的努力被认可。

### [不再糟糕的坏主意 | Devon C. Estes](https://devonestes.com/bad-ideas-that-arent-bad-anymore)

有 15 年从业经验的工程师 Devon C. Estes 在团队回顾会上发现，自己长期依赖的经验直觉正在频繁失效：许多过去被他判定为「坏主意」的做法，如今因为 AI 大幅改变了各种成本结构而变得可行。他列举了团队当前正在实践并见效的做法，包括取消同事互审 PR、把团队拆成相互独立的工作流、不再建议工程师走深度专精路线；同时也在重新审视从零重写、自建而非采购、同一功能做三个版本、引入团队无人掌握的语言或工具等旧禁忌。他得出的结论是：这些规则原本建立在具体成本之上，成本变了规则不会自动更新，因此当直觉说「不行」时，应先追问「当初让它变成坏主意的成本，现在还在吗」。

- 🔄 **取消同事互审 PR**：团队约一个月前彻底取消了「作者之外的人审 PR」这一流程。现在工程师与 Claude 协作，由 Claude 开 PR，持票人（工单负责人）本人审 Claude 的产出，CI 通过且 `Greptile` 审查干净后即可自行合并，不再等同事切换上下文或在 Slack 上催人。他指出，「第二双眼睛」仍然存在，只是作者变成 Claude、审者变成最了解问题的人；小 bug 和不一致由 Claude 与 Greptile 抓得更准，而架构缺陷、产品影响这类大问题本来也很少在评审阶段被发现。
- 🧩 **拆分成独立工作流**：在多人休假、同时存在几条相对独立的工作流时，团队让每人各领一条推进。他过去反对这种安排，因为会形成知识孤岛并削弱团队感；但实际并未出现这些后果，原因是向 Claude 询问「讲讲同事在建的东西是怎么工作的、进展到哪、还差什么」，几分钟就能上手。真正的变化是上下文切换成本骤降——现在只需切换到「问题」层面，理解要解决的问题和方案大致形态即可贡献，不必深入具体代码。
- 🧠 **从深度专精转向判断力**：他给下属的建议从经典「T 型人才」反转为：不必在某个框架或领域（性能、无障碍、分布式系统、Rails/Phoenix 源码级专家）深耕，因为 AI 已读过全部源码并能秒答。仍要打牢工程基本功——架构、抽象设计、判断抽象何时失效并重构、发现并命名缺失的概念——这些决定了高层架构、领域建模与数据建模的质量。同时「技术好」只是入场券，还需懂设计、产品开发、用户研究和业务；只写代码的纯技术岗位价值已明显下降。
- 🔮 **仍在观望的旧禁忌**：几件事他尚未完全改观但已不再笃定：从零重写的最大风险是耗时数年、旧系统还在变，若重写只需数天或数周，风险大幅消退；自建而非采购，当精确满足 100% 需求的工具一个下午就能做出来时，账算得不一样；同一功能写三个版本扔掉两个，如今常比在设计文档里争论更快找到正确方案，甚至可以跳过粗糙原型直接在生产环境对真实用户做 A/B 测试；引入团队没人会的语言或工具，例如团队没有 C# 知识，但它是某款优秀的 ANT+/BLE 接收器唯一可用的驱动。
- 💡 **成本变了，规则没自动更新**：他总结这些「坏主意」当年之所以坏，都是因为某种成本：同事评审值得做是因为否则没人看代码，知识孤岛糟糕是因为上手慢且昂贵，深度专精有价值是因为知识稀缺难得。AI 快速改变了这些成本，但建立在其上的规则和他的直觉不会随之更新——直觉是在成本稳定的 15 年里训练出来的，仍以同样的自信给出曾经正确的答案。他的应对是追问「是什么成本让它成为坏主意，那个成本还在吗」，并更倾向于放行过去会被他否决的实验。
- ⚠️ **效果仍属早期**：新的 PR 流程只运行了一个月，他明确表示「至少目前」感觉良好；拆分工作流是否会有尚未显现的长期后果，他坦言不确定。但他强调，「也许有我们还没看到的问题」与一年前他会说的「我确信这是坏主意、我们会后悔」是两种完全不同的判断。

### [The Explorer Pattern：产品发明与开发。| Irrational Exuberance](https://lethain.com/explorer-pattern/)

Will Larson 提出“Explorer Pattern（探索者模式）”：由一个小型个人或团队先构建可运行实现，尽量降低跨团队与跨职能影响，待原型完成后再与其他团队核对细节，并接受这可能带来大幅返工；文章以 2026 年软件生成与返工成本大幅下降为背景，主张用主从复制式的小组自治、公开进展和非阻塞协作替代传统的重前置协调。

- 🧭 **模式定义**：Explorer Pattern 是由一个个人或团队构建功能性实现，尽可能减少跨团队和跨职能影响；原型完成后再与其他团队对齐细节，并接受初始开发可能需要非常大幅度的返工。
- 🔄 **成本假设**：文章以 2026 年为分界：生成输出、代码、设计和分析在约束、模式与埋点合适时接近免费，返工也极便宜；过去围绕避免工程返工优化，现在应改进系统级流程与自动化集成反馈，若高杠杆流程改进慢于一次性解决，就是流程缺陷。
- 🧩 **主从复制类比**：用 `MySQL`/`PostgreSQL` 主从复制类比：写入在主库验证，下游副本可延迟但不会错；对比 `Dynamo`/`Cassandra` 需多数副本确认，可靠但在固定硬件上通常更慢且可能不一致。模式让绝大部分工作经同一小组，内部一致但不保证业务正确，例如 `200` 是合法整数但不代表信用额度应为 `200`。
- 💬 **非阻塞协作**：其他团队在下游异步获知变化，而非同步前置参与；工作组负责合理化方案并为其他团队创建可见性，让其以非阻塞方式参与。
- 🏢 **Imprint 案例**：Imprint 支持 `Plaid` 等金融聚合器，在 agentic commerce 中更重要；工程负责人 Ron 以低投入在 `private alpha` 中先理解问题形态并定期沟通，完整方案后把跨团队 `replica-lag` 降到近零，解决剩余小问题并发布，项目未正式进入路线图。
- 🎯 **目标与赞助**：每个计划都要有明确结果和赞助人；小项目可不显式，但超过约 3 周若不能明确赞助人且其不会热情认同，就更接近“迷失”而非“探索”。
- 🛠️ **小组规则**：小组最多 5 人且越小越好，成员尽量把整个项目放在脑中；小组要灵活，“找到说 yes 的办法”，探索问题根本形态而非假装已知。
- 📝 **公开进展**：探索者要在公开渠道汇报进展；原文要求同时建立 `Linear Project` 和 `Slack channel`。
- ⚙️ **最窄变更**：对现有系统做最窄可行改动；不必要变更会破坏他人心智模型，若无心变更还会让人误以为有意为之，抑制后续改进且成本很高。
- 🧪 **假设与试错**：快速丢弃坏想法，其余尽快实现以筛选；固定假设避免卡住，如收入预测和伙伴上线日期只需合理锚点而非精确；接受完全错误，准备第二、第三、第四次重来。
- 🚀 **功能开关上线**：从前后端到数据拉取全链路打通并发布到生产，放在仅内部人员启用的 `feature flag` 后，这是探索的第一步。

### [同步的力量 | Seth's Blog](https://seths.blog/2026/11/the-power-of-sync-2/)

Seth Godin 在《The power of sync》中提出用同步/异步轴理解个人与组织协作：同步是共享日程的实时共同工作，异步是按各自日程推进；二者各有成本与收益，组织常低估同步会议的成本并误用异步工具。文章强调在交接点、权力归属、信任建立和AI协作中重新设计工作模式，以保护创作节奏并提升协作效率。

- 🧩 **同步与异步**：同步是共享日程、实时共同工作，异步是按个人日程推进；电话与短信、电视与YouTube/Netflix、剧本创作与拍摄、会议与备忘录、商业航班与私人飞机都是对照，二者各有成本和优势。
- ⚡ **同步的收益**：同步可让能量倍增，贡献者带动他人追赶或超越好点子；也能提高流程效率，例如甜甜圈必须在出炉后立刻上糖霜；贡献者可实时观察接收者反应并调整，还提供命令、控制和检查手段。
- ⚠️ **同步的成本**：同步会导致能量螺旋下降，成员情绪脱节或缺席会拖累整体；弹性与冗余更少，凑齐合适人员成本高；常不匹配员工和市场节奏；难对工作细节与项目弧线保持意图清晰。
- 🔄 **交接点**：现代协作的杠杆和摩擦集中在同步/异步切换的交接点；deadline 是对异步工作施加的同步点，关注模式切换能发现机会与陷阱。
- 🔑 **时钟与假异步**：谁拥有时钟是权力展示：召集会议者已决定占用他人时间，异步把权力从协调者移向创作者；Slack、短信和邮件本是异步工具，却形成实时回复预期，造成同步打断却没有同步能量。
- 📈 **媒体与文化**：媒体公司常因固守既有同步/异步模式而在消费轴翻转时受挫；Netflix 转向 binge viewing 并以资本优势大量产剧，但削弱口碑，Nathan Fielder 电影上线周的讨论多于其流媒体节目；Amazon 和 Netflix 也受既有优势制约，分别对同步内容和实时购物探索不足。
- 🧠 **AI 的异步性**：AI 当前是异步的：agent 不需要会议且可在凌晨3点工作，人类反而成为同步瓶颈；随着能力增强，AI 预计会成为多数同步事件的伙伴。
- 🔗 **信任的建立**：信任在同步中建立、在异步中消耗；异步更适合已相识的人，新团队、新员工和新客户关系初期可能需要同步；替代方案是设计天然异步系统，用在线声誉系统和有思考的在线社区让新参与者建立信任。
- 🎯 **三条准则**：三条准则是：除非同步能带来优于异步的明确优势，否则不要同步，并展示理由捍卫选择；做异步工作时匹配个人内在节律，按不同顺序完成更多；注意同步与异步之间的切换，机会和陷阱都在那里。
- 📝 **命名与定价**：应命名并保护自己的工作方式和交付预期；组织要更有意识地计算同步成本，创作者要按每种工作合理定价，例如请 Bob Dylan 在生日派对演唱要100万美元有其原因。
