### [](https://scotthelme.co.uk/everything-i-learned-shipping-device-bound-session-credentials/)

**原文标题**: [Everything I Learned Shipping Device Bound Session Credentials](https://scotthelme.co.uk/everything-i-learned-shipping-device-bound-session-credentials/)

overview summary
本文記錄了在 Report URI 實際部署 Device Bound Session Credentials（DBSC）時遇到的各種生產環境問題與修復經驗，涵蓋規格理解、競態條件、瀏覽器行為、安全性陷阱與實作建議。

- 📜 規格理解與實際相反：註冊是單階段（回應帶 header，瀏覽器 POST 完成），重新整理是雙階段（先 403 拿 challenge，再簽章 POST 拿新 cookie）；403 是正常流程，不是錯誤。
- 🗄️ 不要把 DBSC 狀態放進 session store：PHP session 整包序列化、last-writer-wins，登入後並發請求會覆寫綁定，導致安全機制靜默失效，必須用獨立 key 儲存。
- 🔄 cookie 與 challenge 每次 refresh 都要輪換；註冊回應不能帶 challenge，否則 Chrome 報 Challenge Error；challenge TTL 必須長於 cookie lifetime。
- ⚡ 單層歷史寬容視窗：refresh 期間舊 cookie 仍會被合法請求使用，直接比對會誤判為被盜並登出；應接受「前一世代」cookie，且寬容期限等於其在瀏覽器的自然壽命。
- 🚫 絕不能 redirect DBSC endpoint：若 refresh 收到 302，Chrome 會永久死鎖（deferred navigation 永不恢復）；應回 401，讓瀏覽器終止 DBSC session 並正常導向登入。
- 🛡️ Challenge mismatch 不等於攻擊：簽章驗證已通過即證明持有私鑰；mismatch 僅代表並發、重試或傳遞競態，應視為良性可重試，發新 challenge 回 403，只有壞簽章才終止。
- 🔗 SSO 登入（如 SAML）常無法綁定：cross-site 情境下 Lax cookie 被 withheld，註冊 POST 401 且不會重試；應記錄綁定意圖，在下一個非 cross-site 文件請求時才真正發起。
- 🔓 邊緣 fail open、閘口 fail closed：不支援 DBSC 的瀏覽器自然降級為普通 cookie 認證；但損毀的 binding 若被視為「無 binding」會靜默降級成 bearer token，必須將「無紀錄」與「無法解析」分開處理。
- ⚖️ 刻意不對稱設計：cookie 保留上一世代，challenge 則丟棄前一世代，避免 replay 且符合並發收斂；不提供軟體金鑰 fallback，以免失去硬體綁定價值。
- 📦 其他實務細節：不驗證非必要的 JWT 宣告（iat/exp 等）；空回應也設定 content type，避免 debug bar 注入 HTML 造成混淆。
- ✅ DBSC 值得採用：能封閉 MFA 無法解決的 stolen cookie 漏洞，且不會鎖住用戶；但 refresh endpoint 絕不能 redirect。
